# تجربة منحنى الحجم — RIDI-RAG-QWEN3-SCALE-CURVE-v1

السؤال اللي تجاوب عليه: هل النماذج الأكبر تتخلص من المشكلة؟ نفس الـ800 سؤال، ونفس التبديل، ونفس البرومبتات، على ستة أحجام من Qwen3 (من 0.6B إلى 32B)، مع أرضية تنفيذ لكل حجم.

## محتويات الحزمة
| الملف | وش هو |
|---|---|
| `preregistration/OSF_Preregistration_RIDI-SCALE-CURVE-v1.md` و`.docx` | نص التسجيل المسبق، جاهز تنسخه في نموذج OSF |
| `code/models.json` | النماذج والإصدارات. إصدارا 8B و32B مثبّتين، والباقي يتعبّى قبل القفل |
| `code/resolve_revisions.py` | يجيب بصمات الإصدارات من Hugging Face ويعبّيها في `models.json` |
| `code/make_lock.py` | يسوي `LOCK.json`، وهو بصمات الكود والنماذج. المشغّل يرفض يشتغل إذا تغيّر أي ملف |
| `code/run_scale_curve.py` | المشغّل: نموذج واحد × مجموعة واحدة في كل تشغيل |
| `code/aggregate_scale_curve.py` | التحليل المحدد مسبقاً (H1–H3 والتحليلات الثانوية S1–S6) |
| `tests/make_synthetic.py` | اختبار بالبيانات المصطنعة فقط، يتأكد إن التحليل يشتغل. **ليست نتائج** |

## الخطوات بالترتيب (لا تغيّر الترتيب)

**1. عبّي الإصدارات** على جهاز فيه إنترنت وhuggingface_hub:
```
python3 code/resolve_revisions.py
```
**2. اقفل الكود:**
```
python3 code/make_lock.py
```
**3. انشر قبل أي تشغيل:**
- انسخ الحزمة كاملة إلى المستودع في `experiments/qwen3_scale_curve/` (بحيث يبقى `code/` و`preregistration/` داخله)، وسوِّ commit وpush.
- سجّل على OSF بنص التسجيل المسبق، وأرفق `LOCK.json` و`models.json`، واذكر رقم الـcommit.

**4. شغّل الوظائف** على GPU بسعة 80GB (A100 أو H100). كل نموذج يحتاج أربع وظائف:
```
python3 code/run_scale_curve.py --model-key qwen3-0.6b --dataset nq \
  --control-zip RIDI_RAG_NATURE_CONTROL_POSTREG_20260902.zip \
  --data-zip prepared-v4-nq.zip \
  --primary-results-zip RIDI_RAG_RESULTS__PRIMARY_H1_H2.zip \
  --out ridi_scale_out
```
- كرّرها لكل `--model-key` من 0.6b إلى 32b، ولكل `--dataset` من nq وhotpotqa وfever وscifact.
- ملفات المصدر هي نفس أرشيفات 2 سبتمبر اللي استخدمتها لتجربة 32B، ولازم بصماتها تطابق.
- لو الأرشيفات على Firestorage، استخدم `--control-share` و`--data-share` و`--primary-results-share` بدل المسارات.
- لو فشلت وظيفة لسبب تقني، أعد تشغيلها بنفس الأمر مع `--attempt 2`، وبحد أقصى `--attempt 3`. يجب الاحتفاظ بمجلد المحاولة السابقة وحالتها؛ لا يسمح المشغّل بالكتابة فوقها أو بإعادة وظيفة ناجحة. لا تُعدّ الحالة `blocked` فشلًا تقنيًا يسمح بالإعادة التلقائية.

**5. لا تفتح أي ملف نتائج** لين تخلص كل الوظائف.

**6. حلّل مرة وحدة:**
```
python3 code/aggregate_scale_curve.py ridi_scale_out --features code/per_question_features.jsonl
```
`code/per_question_features.jsonl` نسخة حرفية من Supplementary Data 3 في حزمة v14.3؛ بصمتها مسجلة في `LOCK.json`. يطلع لك `SCALE_CURVE_RESULTS.json` و`.md`.

## الوقت والموارد
- تشغيل 32B السابق أخذ حوالي 15 دقيقة لكل مجموعة على A100 واحد، لشرطين.
- هنا ثلاثة شروط، والشرط الثالث بدفعات أسرع.
- المجموع لكل الأحجام حتى 32B تقريباً ساعات قليلة على GPU واحد.
- نموذج 235B اختياري، ويحتاج 8 بطاقات 80GB.

## وش تعني النتيجة
- **H1 supported:** الأثر باقي عند 32B. هذي الجملة اللي تقوّي الاستفسار: «التوسيع لا يغلق النقطة العمياء».
- **H3 decreasing مع H1 supported:** «يقل مع الحجم لكنه يبقى حتى 32B». وهذي نتيجة قوية كمان.
- **H1 falsified:** الأثر يختفي عند 32B. نتيجة صادقة تنشرها، وتوجّه الورقة لـNature Machine Intelligence.

S4 تقيس هل نفس الأسئلة تتغير في كل الأحجام. لو طلعت مركّزة، فهذا يدعم وجود أسئلة أكثر عرضة لتغيّر الصحة عبر الأحجام المختبرة، دون إثبات أن السبب مستقل عن النموذج. وهذه ممكن تكون زاوية اكتشاف إضافية.

## اللي ما سويته
ما شغّلت المشغّل، لأنه يحتاج GPU وأرشيفات المصدر، وهي مو عندي. المشغّل مبني على سكربت 32B اللي اشتغل فعلاً، مع إضافة شرط الدفعات وفحوص الحتمية. سكربت التحليل اختُبر على بيانات مصطنعة واشتغل كامل.

## فحص التنفيذ قبل القفل

أُصلحت قبل القفل حدود المقارنة العددية، وحفظ المحاولات والفشل، والتحقق من اكتمال الوظائف وبصمات النتائج. التفاصيل في `PRELOCK_REPAIRS.md`. لم تتغير الفرضيات أو العتبات أو البذور أو الشروط.

الخيار `--preflight-only` يتحقق من الأرشيفات واللوحة والبرومبتات فقط؛ لا يحمل نموذجًا ولا يولّد إجابات ولا يستهلك محاولة.
