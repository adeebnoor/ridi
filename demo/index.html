How to use RIDI

From two score files to an identity audit in three steps.

You need a stable entity identifier, a score for each version, and a declared capacity k. Keep the identity column private when domain governance requires it.

1

Prepare two versions

Each file should contain the same stable entity ID and a score column.

id,score A001,0.912 A002,0.901 ...
2

Run the audit

Compare the two score versions at one or more finite capacities.

ridi-audit compare \ --r0 scores_v1.csv \ --r1 scores_v2.csv \ --id-col id \ --score-col score \ --k 50 100 \ --report audit.md
3

Report what changed

Do not stop at RIDI. Report capacity, overlap, changed seats, and domain-appropriate justification.

capacity k: 50 overlap: 32 / 50 changed seats: 18 RIDI: 0.529 entrants/exits: audited justification: pre-specified
Worked example

A reproducible interpretation, not just a number.

Suppose a cybersecurity queue can remediate only 100 vulnerabilities per cycle. A model update retains 70 of the original 100.

Capacity-limited remediation queue

Version 1 and version 2 both produce a top-100 action set. Seventy vulnerabilities stay in the queue; thirty leave and thirty enter.

RIDI = 0.462

Because RIDI = 1 − 70/130. The operational interpretation is clearer than the scalar: 30% of action capacity was reassigned.

Scientific boundary

RIDI measures allocation turnover. It does not by itself establish correctness, fairness, causal harm, clinical benefit, or model superiority. Large turnover can be justified; zero turnover can be undesirable. The scientific requirement is to make allocation identity observable and testable.
